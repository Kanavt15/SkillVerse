## 1. Product and current position

SkillVerse is a skill-sharing platform: learn through courses, teach others,
discuss lessons and prove completion. The longer-term marketplace adds paid
courses, mentoring, skill swaps, practice, exam credentials and subscriptions.
India-first commerce is planned in INR through Razorpay; global payments follow
through a provider adapter in a later phase.

The Express/MySQL/Redis application has already been replaced in this working
tree. The current application is a TypeScript monorepo running on Cloudflare
Workers, with a Hono API, React Router SSR website and D1/Drizzle database.

## 2. Architecture: existing implementation and later extensions

| Area            | Current implementation                                                 | Planned extension                                            |
| --------------- | ---------------------------------------------------------------------- | ------------------------------------------------------------ |
| API             | Workers, Hono, TypeScript; routes -> services -> repositories/policies | Payment adapter, queue consumers, scheduled jobs             |
| Website         | React 19, React Router 7 SSR, same-origin API binding or authenticated Vercel server proxy          | Marketplace, practice, mentoring and organization pages      |
| Database        | D1/SQLite, Drizzle and reviewed migrations                             | Commerce and later tables introduced with their features     |
| Search          | D1 FTS5, filters and pagination                                        | Demand analytics and semantic search                         |
| UI              | Tailwind 4, owned shared components, Radix, Lucide, Motion             | Add primitives only when a component has a clear need        |

| Media           | YouTube/Vimeo links, articles, authored timelines, practice quizzes    | Direct R2 uploads, quarantine and protected media            |

| Email           | Resend integration; local mailbox when provider is unconfigured        | Durable outbox, Queues, retries and delivery monitoring      |
| Flags/cache     | D1 flags and Worker-isolate memory cache                               | Admin controls; KV only if measured usage justifies it       |
| Background work | Request-associated work and bounded five-minute cron maintenance                                   | Queues for larger workloads               |
| Testing         | Vitest/workerd/D1, components, Playwright, axe                         | Provider/staging journeys, performance, manual accessibility |

Production keeps website and /api on one origin. The selected frontend is Vercel
SSR with a private authenticated proxy to the Cloudflare API; the optional
Cloudflare website uses a service binding. API authorization remains authoritative. Local development uses web
port 5173 and API port 8787, without local MongoDB, Redis or MySQL installation.

Writes that must succeed together use atomic D1 batches, conditional guards,
idempotency and audit/history receipts. Preserve permissions and enrolled learner
access when adding revisions, restoration and commerce. Introduce only tables
needed by the active phase. Current schema modules: identity, platform, catalog,
learning, quizzes, community, notifications and privacy. Reference:
docs/architecture/database-schema.md.

## 3. Design and data rules

Keep the professional learning-studio direction: quiet harbor-blue/slate surfaces,
Manrope UI text, Bricolage Grotesque headings, clear reading space and restrained
motion. Retain light/dark themes, responsive workspaces and native forms.

The hero already has search, a connected learning diagram, an animated scroll-down
cue and scroll-driven motion. Preserve its native discovery link, reduced-motion
behavior and usable content without JavaScript.

Use actual API content and honest empty states. Never invent testimonials,
profiles, activity counts, reviews, sales or revenue. Development seeds and test
fixtures stay local and clearly identified; do not seed demo content into a live
production catalog. Preserve functionality during visual changes.

Performance targets: initial homepage JavaScript below 180,000 bytes gzip, LCP
below 2.5 seconds and CLS below 0.05 under a documented test profile. Last measured
initial graph: 178,322 bytes gzip across 34 static chunks. Production metrics and
operating budgets still require measurement.

## 5. Business and launch rules

Planned revenue: course sales, wallet/credits/gifts, ads/referrals, paid exams,
mentoring, subscriptions, sponsored listings, affiliates, cohorts, teams,
recruiting and contest sponsorships. None of these paid streams is currently live.
Free learning/community provide the first usable product.

Proposed splits, prices and refund windows are documented in
docs/business/revenue-model.md and partly seeded as defaults. Validate commercial
terms before launch; build admin editing/validation/audit rather than assuming a
settings table is an existing admin application.

Before real sales, verify test-mode payment, webhook, entitlement, ledger, refund
and reconciliation journeys. Confirm provider activation and obtain appropriate
review of tax/invoicing, payout/KYC, privacy, retention, cancellation, age eligibility
and grievance requirements. See docs/business/compliance.md; documentation alone
is not completion.

Ads are a separate release. Require approval and applicable consent before third-
party scripts load. Exclude player, checkout, exams, auth, settings and admin;
reserve layout space and label promotions. Ads approval does not block commerce
that leaves advertising disabled.

## 6. Security and privacy acceptance

Maintain server sessions, verified-email/role/ownership checks, staff MFA,
Origin/client-header CSRF checks, rate limits, strict validation, parameterized
SQL, escaped/sanitized content, CSP nonces, redacted logs and secret handling.
Keep the local MFA exception out of deployed environments.

Remaining controls include privileged role provisioning, account export/deletion,
step-up/privilege-change review, production Access verification, secret scanning,
dependency/action hardening and recovery checks. Track them in TODO.md and
docs/security/; unit tests alone do not establish complete ASVS compliance.

Future uploads need bounded direct-storage authorization, quarantine and private
access. Future webhooks need raw-body signature checks, unique events and atomic
settlement. Future code execution needs isolation; never execute learner code via
host child_process. Future exams need server timing and protected answer keys.

## 7. Development, documentation and validation

Local setup: npm run setup, then npm run dev. Migrations are forward-only reviewed
SQL in packages/db/migrations; never rewrite applied SQL. Keep database and
certificate-signing-key recovery instructions together, storing secrets separately.

For functional increments, run appropriate checks: npm run check,
npm run format:check, npm run build and affected browser journeys. Browser fixtures
use isolated local mail/Turnstile configuration and retain real rate limits.
Documentation-only changes require docs/link and formatting checks, without
application-data mutations or deployments merely to verify prose.

Update README, relevant architecture/API/security/schema docs, CHANGELOG, TODO.md
and phase records with features. Add new ADRs for major decisions; do not edit
accepted ADR history. Keep file-purpose comments, folder guides and beginner docs
accurate and useful.

Last functional baseline in this session: 247 automated tests, all 15 Chromium
journeys across a full run and corrected targeted rerun, production build, types,
lint, formatting and docs checks. This is local verification, not staging or
production certification. Re-measure when implementation changes.

## 8. Deployment and operating budget

Separate local, staging and production resources/secrets. Provision services used
by the current release: D1, API/web Workers, service binding, notification Durable
Object and provider/security configuration. Add R2, Queues, KV or AI services only
when their code is ready, not solely because they appear in this plan.

Replace deployment placeholders, apply migrations before dependent code, configure
same-origin routing/staff Access, verify Google/Turnstile/email, then run staging
smoke checks. Confirm rollback, monitoring, backups and restore rehearsal before
production. Instructions: docs/operations/deployment.md and backups.md.

Free tier first for development/demos. Measure CPU, requests, D1 rows, storage and
email volume against current provider limits; avoid promises of zero cost,
guaranteed latency or a fixed supported user count. Upgrade services only when
measurements justify it and the user authorizes it.
